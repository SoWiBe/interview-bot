# ТЗ: утренняя сессия v2

Статус: разделы 2–8 реализованы в ветке `feature/session-v2` с вариантами по умолчанию из раздела 8. Раздел 9 (сервер) — впереди.

## 1. Зачем

Что не так сейчас:

1. **Любое сообщение = решение.** Любой текст без команды уходит на ревью (`BotUpdateDispatcher.HandleMessageAsync` → `PracticeService.ReviewAttemptAsync`). Задал уточняющий вопрос — получил «1 из 5».
2. **Слишком тяжело.** Условия намеренно скупые и со скрытыми неоднозначностями, теория на 3–5 минут с продакшн-кейсом из highload, ревью из девяти полей, плюс разбор кода из `dotnet/runtime`.
3. **Нет понятной структуры дня.** Набор зависит от темы и чётности дня: то SQL есть, то нет.

Что должно получиться: одна предсказуемая сессия каждое утро, написанная простым языком, где с ботом можно разговаривать, а оценка ставится только за то, что я сам назвал решением.

Порядок работ: сначала сессия v2 (разделы 2–8), потом выкладка на сервер (раздел 9).

## 2. Сессия

Одна сессия в день, приходит утром по расписанию (как сейчас, `/today` — получить сразу).

| Шаг | Что | Язык | Время | Сложность |
|---|---|---|---|---|
| 0 | Теория | — | ~2 мин чтения | вход в рабочий режим |
| 1 | Задача-разогрев | SQL | ~5 мин | лёгкая, без подвохов |
| 2 | Основная задача | SQL | ~10–15 мин | средняя |
| 3 | Задача | C# | ~15 мин | средняя |

### 2.1. Порядок выдачи

- Утром приходят теория и задача 1. Набор генерируется за 15 минут до времени отправки, чтобы прийти вовремя; по `/today` теория приходит сразу, как готова, первая задача — следом.
- Следующая задача приходит по кнопке «➡️ Следующая задача» — она есть под ревью и под открытым решением.
- Под последней задачей кнопка «🏁 Завершить сессию» — итог сессии: оценки по задачам, серия, задавал ли уточняющие вопросы.
- Незаконченная сессия на следующий день не продолжается: утром начинается новая. `/today` в течение дня возвращает к текущему шагу и ничего не отправляет повторно.

Задачи идут по одной, чтобы в каждый момент была ровно одна «текущая» — тогда сообщение без reply однозначно относится к ней.

### 2.2. Теория (шаг 0)

- Тема выбирается как сейчас: очередь из `curriculum.yaml` + интервальное повторение. Кнопки «Понял / Повторить / Пробел» остаются.
- Одна мысль за раз. Состав: суть (2–3 предложения) → пример из жизни → короткий код (до 10 строк) → 2 вопроса для самопроверки.
- Блок «код из реального репозитория» из утренней сессии убирается (см. 8.1).

### 2.3. SQL (шаги 1 и 2)

- Обе задачи — на одной схеме (2–3 таблицы). Схема даётся как `CREATE TABLE` + 3–5 строк примера данных.
- В задаче 2 схема повторяется свёрнутым блоком, чтобы не листать чат.
- Разогрев: одна конструкция (фильтр, простой `JOIN`, `GROUP BY`). Условие однозначное.
- Основная: `HAVING`, `COUNT(DISTINCT)` при `JOIN`, оконные функции, топ-N в группе — по кругу. Если тема дня из модуля SQL, основная задача — по теме дня.

### 2.4. C# (шаг 3)

Категории, по кругу (берётся та, что давно не выпадала; категория хранится в задаче):

1. **Алгоритмы** — бинарный поиск, два указателя, окно, хеш-таблица.
2. **Потоки и async** — отмена, таймаут, ограничение параллелизма, блокировки.
3. **Написать участок кода** — retry с backoff, кэш с TTL, rate limiter, батчинг, метод-расширение.
4. **Найти и починить баг** — дан код на 15–25 строк с ошибкой.
5. **Коллекции и LINQ** — выбор структуры данных, запрос, отложенное выполнение.

Если тема дня не из SQL — задача по теме дня, в ближайшей по смыслу категории.

## 3. Диалог и отправка решения

Главное изменение. Сообщение пользователя **никогда не оценивается само по себе**.

### 3.1. Два режима

| Режим | Когда | Что делает бот |
|---|---|---|
| **Диалог** (по умолчанию) | Любой текст по задаче, пока не нажата «Отправить решение» | Отвечает как интервьюер. Без оценки, без записи попытки. |
| **Решение** | Нажата «📤 Отправить решение», следующее сообщение — решение | Делает ревью с оценкой, сохраняет попытку. |

### 3.2. Кнопки под задачей

`📤 Отправить решение` · `💡 Подсказка` · `🏳 Показать решение`

### 3.3. Диалог

- Сообщение относится к задаче, если это reply на задачу или на любое сообщение бота по ней. Без reply — к текущей задаче сессии.
- Бот отвечает на уточняющие вопросы **по существу и одинаково каждый раз**: ответы на неоднозначности генерируются вместе с задачей и хранятся в ней (новое поле `clarifications`), эталонное решение им соответствует.
- На «правильно ли я думаю?» бот наводит, но готовый код не пишет.
- «💡 Подсказка» — следующий шаг к решению с учётом уже сказанного. Каждая следующая подсказка конкретнее предыдущей.
- Если сообщение в диалоге похоже на готовое решение, бот его **не оценивает**, а отвечает: «Похоже на решение. Проверить?» с кнопкой `📤 Проверить это как решение` — чтобы не пересылать текст заново.
- Переписка хранится и передаётся в модель при каждом ответе и при ревью.

### 3.4. Отправка решения

1. Нажал «📤 Отправить решение» → бот: «Жду решение следующим сообщением» + кнопка `↩️ Отмена, у меня ещё вопрос`.
2. Следующее текстовое сообщение (reply не нужен) — решение. Режим ожидания сбрасывается.
3. Команды в режиме ожидания работают как обычно и режим не сбрасывают.
4. Под ревью: `➡️ Следующая задача` · `🔁 Отправить ещё раз` · `👀 Показать решение`.

Попыток может быть несколько; в статистику идёт лучшая.

### 3.5. Что видит ревью

Ревью получает переписку, поэтому «задал ли уточняющие вопросы» считается по диалогу, а не по тексту решения. Взятые подсказки учитываются в оценке и упоминаются в ревью.

## 4. Проще и понятнее

Правится в `Prompts.cs` (и схемы в `ContentSchemas.cs`).

### 4.1. Общий тон

- Объяснять как коллеге, который тему подзабыл: короткие предложения, обычные слова.
- Термин при первом появлении — с пояснением в скобках.
- Сначала пример, потом правило.
- Профиль студента и список пробелов остаются, но как подсказка, о чём давать задачи, а не как повод усложнять.

### 4.2. Задачи

| | Сейчас | Станет |
|---|---|---|
| Условие | намеренно скупое | понятное: что дано, что вернуть, пример входа и выхода |
| Неоднозначности | несколько скрытых в каждой | разогрев — 0; остальные — ровно одна, ответ на которую меняет решение |
| Уточняющие вопросы | 2–5 ожидаемых | 0–2 |
| Объём | 15 минут на каждую | 5 / 10–15 / 15 минут |
| Разбор решения | 3–6 предложений | идея в 1–2 предложениях + шаги по пунктам |

### 4.3. Ревью

Вместо девяти полей — четыре блока:

1. **Итог** — одна строка: работает / работает с замечаниями / не работает, и оценка.
2. **Что хорошо** — 1–2 пункта, только по факту.
3. **Что поправить** — не больше трёх пунктов, от важного к мелкому, с указанием места в коде.
4. **Исправленный код** — только если есть что исправлять.

Оценка 1–5 остаётся, с расшифровкой: 5 — принял бы без вопросов, 4 — мелкие замечания, 3 — идея верная, есть ошибки, 2 — идея не та, 1 — решения нет. Пропущенный уточняющий вопрос снижает оценку не больше чем на 1.

## 5. Команды

| Команда | Изменение |
|---|---|
| `/today` | Запускает сессию или возвращает к текущему шагу |
| `/next` | Доп. задача вне сессии; тип выбирается кнопками: SQL / C# |
| `/topic <название>` | Теория + одна задача по теме |
| `/giveup` | Без изменений, дублирует кнопку «Показать решение» |
| `/stats` | Добавляется: сколько сессий пройдено полностью |
| `/pause`, `/settings` | Без изменений |

Тексты `/help` и `/start` переписываются под новую схему.

## 6. Изменения в коде

**Данные** (одна миграция EF, старые записи остаются валидными):

- `PracticeTask`: `Role` (Warmup / Main), `Category`, `Clarifications`, `ClosedAt`, `AwaitingSolutionSince`.
- Новая таблица `TaskMessage`: `TaskId`, автор (пользователь / бот), текст, `TelegramMessageId`, время. Используется и для маршрутизации reply, и как история для модели.
- `TaskAttempt`: `HintsUsed`.

**Логика:**

- `Core`: шаг сессии и переход между шагами — чистая функция с тестами (по образцу `DailyPlanner`); выбор категории C#-задачи по кругу.
- `DigestService`: `DailyTaskRequests` → три фиксированных запроса; SQL-схема генерируется один раз на обе задачи.
- `DigestDelivery`: задачи отправляются по одной, захват отправки — на задаче (`SentAt`), а не на всём блоке.
- `PracticeService`: `ReviewAttemptAsync` вызывается только из режима «Решение»; новый метод для ответа в диалоге и подсказки.
- `BotUpdateDispatcher`: маршрутизация текста по режиму, новые callback-кнопки.
- `IContentGenerator`: + ответ в диалоге; структура ревью меняется.

## 7. Критерии приёмки

1. Утром приходят теория и одна SQL-задача; вторая и третья — только после закрытия предыдущей.
2. Вопрос reply'ем на задачу → ответ по существу, без оценки, в `TaskAttempt` ничего не появилось.
3. То же сообщение без reply → относится к текущей задаче.
4. «Отправить решение» → следующее сообщение → ревью с оценкой, одна запись в `TaskAttempt`.
5. «Отмена» в режиме ожидания → следующее сообщение снова диалог.
6. Код, отправленный без кнопки, не оценивается; бот предлагает проверить его как решение.
7. Один и тот же уточняющий вопрос, заданный дважды, получает один и тот же по смыслу ответ.
8. Задавал вопросы в диалоге → в ревью и в `/stats` это засчитано.
9. Обе SQL-задачи используют одну схему.
10. За 5 дней подряд C#-задача не повторяет категорию.
11. Повторный `/today` и рестарт бота посреди сессии ничего не дублируют.
12. Существующие тесты проходят, добавлены тесты на шаги сессии и выбор категории.

## 8. Вопросы на согласование

Везде указан вариант по умолчанию — если возражений нет, делаем его.

1. **Код из `dotnet/runtime`.** По умолчанию: убрать из утренней сессии, код провайдера оставить выключенным через настройку. Альтернатива — оставить отдельной командой `/code`.
2. **Выходные.** Сейчас по умолчанию одна задача-повторение. По умолчанию для v2: оставить как есть (`/settings weekend full` — полная сессия). Альтернатива — полная сессия каждый день.
3. **Выдача задач.** По умолчанию: по одной (раздел 2.1). Альтернатива — все три сразу утром.
4. **Решение одним сообщением.** По умолчанию: да, до 4096 символов. Длинное решение, разбитое Telegram'ом на части, не склеивается.
5. **Уровень сложности как настройка** (`/settings level`). По умолчанию: не делаем, уровень зашит в промпты.

## 9. Выкладка на сервер

Делается после приёмки v2. Бот работает через long polling: входящие порты, домен и сертификат не нужны.

### 9.1. План

- Отдельный compose-проект в своей папке (например `/opt/interview-bot`), со своим контейнером PostgreSQL и своим volume. С backend'ом ничего общего, кроме хоста.
- `docker-compose.prod.yml` поверх базового:
  - **порты наружу не публикуются** — сейчас в `docker-compose.yml` заняты `127.0.0.1:5432` и `127.0.0.1:8080`, на сервере с backend'ом они почти наверняка уже используются;
  - healthcheck контейнера бота через `/health/ready` внутри сети compose;
  - лимиты памяти и ротация логов Docker (`max-size`, `max-file`).
- `.env` создаётся на сервере руками, права `600`, в git не попадает.
- Обновление: `git pull && docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build`. Миграции применяются при старте.
- Бэкап: ежедневный `pg_dump` по cron, хранить 7 последних.
- Перед запуском на сервере остановить локальный экземпляр: два процесса с одним токеном будут выбивать друг другу long polling.

### 9.2. Что нужно узнать про сервер

1. ОС и есть ли Docker с compose plugin.
2. Сколько свободной памяти (сборка образа с .NET SDK на сервере требует ~1.5–2 ГБ; если мало — собирать образ в GitHub Actions и тянуть из GHCR).
3. Доступны ли с сервера `api.telegram.org`, `openrouter.ai`, `api.github.com`.
4. Как выкладывается backend (руками, CI) — чтобы сделать так же.
5. Нужно ли переносить текущий прогресс из локальной БД или начинаем с чистой.
